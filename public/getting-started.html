Using the command examples

Commands are templates, not executed results. Run them only against your assigned training target. Replace the placeholders and check required tools first. Commands that run on the target are labelled; your local shell variables are not automatically present in a remote shell. Product versions and historical screenshots are examples, not guarantees about the current lab. 

# In your Linux lab VM; replace these before using later examples.
export TARGET='REPLACE_WITH_ASSIGNED_LAB_IP'
export LHOST='REPLACE_WITH_YOUR_TUN0_IP'
export WORDLIST='/usr/share/seclists/Discovery/Web-Content/common.txt'
mkdir -p ~/htb/getting-started/{scope,notes,scans,logs,evidence,transfers}
cd ~/htb/getting-started

01. Infosec Overview

Information security protects confidentiality, integrity and availability. A pentest is a scoped investigation that turns technical weaknesses into evidence of business risk. Distinguish offensive testing from defensive monitoring, and separate a reproducible finding from an untested suspicion. Risk work includes discovering threats, estimating likelihood and impact, selecting a response and checking whether conditions change.

Practice checkpoint: For one lab weakness, explain which part of the CIA triad is affected and what a defender could change.

02. Getting Started with a Pentest Distro

Use an isolated Linux lab VM or HTB Pwnbox. Parrot is the course example; understanding the operating system matters more than collecting tools. Keep a clean baseline, snapshots and a repeatable setup checklist. Record architecture and tool availability before blaming an exploit. Keep unrelated personal and assessment data outside the lab environment.

Practice checkpoint: Identify your OS, architecture and available tools; record the snapshot or Pwnbox session you used. 

cat /etc/os-release
uname -m
command -v nmap curl nc ssh python3 tmux

03. Staying Organized

Keep scope, notes, scans, logs, evidence and transfer files in separate folders. Each attempt should connect a hypothesis to a command, an observation and a next action. Save useful techniques in a reusable reference, while keeping machine-specific evidence with that machine. Credentials and VPN profiles belong in protected local storage, not a public write-up.

Practice checkpoint: Create the folder layout and record one command with its expected and actual result. 

mkdir -p ~/htb/getting-started/{scope,notes,scans,logs,evidence,transfers}
cd ~/htb/getting-started
find . -maxdepth 2 -type d
# Optional terminal transcript; type exit when finished.
script -a logs/session.log

04. Connecting Using VPN

The lab VPN adds a tunnel interface and routes to the training network. A connected-looking terminal alone does not prove that the assigned target is reachable. Check the client completion message, tunnel address and route selection separately. The profile must match Academy access; the main HTB platform can use a different profile. Figure A illustrates the network boundary.

Practice checkpoint: Explain which route will carry traffic to your assigned target, then verify it. 

sudo openvpn /path/to/your-academy-profile.ovpn
# In another terminal:
ip -br address show tun0
ip route
ip route get "$TARGET"

05. Common Terms

A shell interprets commands. A port identifies a transport endpoint; the service listening there speaks an application protocol. An open port is an observation, not proof of a vulnerability. HTTP is a request/response protocol used by web applications; SSH provides authenticated remote access. Know the difference between your local shell and a shell running on the target.

Practice checkpoint: Label the local host, remote host, protocol and port for one connection. 

id
ps -p $$ -o comm=
ss -lntup

06. Basic Tools

SSH provides authenticated remote sessions. Netcat can open a basic TCP connection and inspect a service banner. Tmux keeps independent terminal panes available for scanning, a listener and notes; Figure B shows this arrangement. Vim is a terminal editor. Learn how to save and exit before editing anything important: insert mode uses i; Escape returns to normal mode; :wq saves and exits; :q! abandons changes.

Practice checkpoint: Use separate terminal panes for observation and notes. Practise editing a disposable file. 

ssh LAB_USER@"$TARGET"
nc -nv "$TARGET" 22
tmux new -s htb
vim notes/session.md
# Tmux: Ctrl-b then % splits vertically; Ctrl-b then d detaches.
# Resume later:
tmux attach -t htb

07. Service Scanning

Enumerate the assigned host before selecting an exploit. Start with a manageable scan, widen coverage, then inspect the services on discovered ports. Save raw output so you can revisit assumptions. Product banners can be incomplete or misleading, and distribution backports mean a version number alone does not establish exploitability. Enumerate FTP, SMB and HTTP with tools that understand those protocols.

Practice checkpoint: Build a table of port, protocol, observed product/version, evidence and next test. 

nmap -sV --open -oA scans/initial "$TARGET"
nmap -p- --open -oA scans/all-tcp "$TARGET"
# Example focused follow-up: replace 22,80 with discovered ports.
nmap -sC -sV -p 22,80 -oA scans/focused "$TARGET"
# Optional protocol-specific checks when these services are in scope:
smbclient -N -L "//$TARGET"
ftp -p "$TARGET"

08. Web Enumeration

Inspect the page, response headers, HTML source, links and redirects before guessing paths. Technology detection suggests hypotheses; validate them against direct evidence. Directory discovery can reveal functionality that is absent from navigation. robots.txt is a clue, not access control. A status code needs context: compare response size and body to detect wildcard or custom error pages.

Practice checkpoint: For every interesting URL, record status, what it exposed and why it changes your next step. 

curl -i "http://$TARGET/"
curl -s "http://$TARGET/robots.txt"
whatweb "http://$TARGET/"
gobuster dir -u "http://$TARGET/" -w "$WORDLIST" -o scans/web-paths.txt

09. Public Exploits

Search with an observed product and version, then read the exploit and its prerequisites. Check authentication requirements, platform, architecture, affected configuration and expected side effects. Metasploit options distinguish the remote target from the address that receives a callback. A framework check is evidence to assess, not a universal guarantee. Do not run an unknown downloaded program just because its title looks relevant.

Practice checkpoint: Write a short applicability checklist before attempting one lab proof of concept. 

searchsploit "PRODUCT VERSION"
msfconsole
# Inside msfconsole:
search PRODUCT
info MODULE_NAME
# After selecting the matching module:

10. Types of Shells

A reverse shell connects from the target to your listener; a bind shell listens on the target for your client. A web shell receives commands through HTTP and may not behave like an interactive terminal. Identify which host runs each command, the connection direction and the effective account. A PTY can improve terminal behavior, but does not grant extra privileges.

Practice checkpoint: Draw the connection direction and verify the identity of the account you obtained. 

# Your lab VM: listen on the address reachable through the VPN.
nc -lvnp 4444
# Inside an existing authorized Linux target shell:
id
whoami
command -v python3
python3 -c 'import pty; pty.spawn("/bin/bash")'
# A bind-shell client connection, if a lab exercise explicitly sets one up:
# nc "$TARGET" TARGET_LISTENER_PORT

11. Privilege Escalation

Initial code execution often runs as a limited account. Investigate its identity, group memberships, sudo rules, file permissions, scheduled tasks and installed software. A useful path depends on a specific trust relationship: for example, a privileged process consuming a file writable by a less privileged account. Enumeration scripts suggest leads; verify them manually. Prefer well-understood misconfigurations over unstable kernel attacks.

Practice checkpoint: For a candidate escalation, identify the controlled input, privileged consumer and evidence of the boundary failure. 

id
uname -a
sudo -l
ls -ld /etc/cron* /var/spool/cron 2>/dev/null
find / -perm -4000 -type f 2>/dev/null

12. Transferring Files

Move only the files needed for the lab. Keep a dedicated transfer directory, avoid accidentally serving your whole home folder, and stop the temporary server afterward. HTTP is convenient; SCP uses an authenticated encrypted session. Base64 represents bytes as text but does not encrypt them. Compare hashes to distinguish a transfer problem from an execution problem.

Practice checkpoint: Transfer a harmless text file and verify the same SHA-256 hash at both ends. 

# Your VM: serve only the transfer directory.
cd ~/htb/getting-started/transfers
python3 -m http.server 8000 --bind "$LHOST"
# Target shell: replace VPN_IP with your VM tunnel address.
curl -f http://VPN_IP:8000/example.txt -o /tmp/example.txt
sha256sum /tmp/example.txt
# Alternative from your VM when SSH credentials are available:
scp example.txt LAB_USER@"$TARGET":/tmp/example.txt

15. Nibbles - Enumeration

The Nibbles case study joins the earlier skills into a chain: enumerate a Linux host, investigate its web application, obtain initial access and examine a privileged file relationship. Begin by collecting service evidence, not by assuming the historical walkthrough IP is still your target. Save an initial scan and a focused follow-up. Explain why each exposed service deserves its next test.

Practice checkpoint: Produce your own service inventory before opening the next walkthrough stage. 

nmap -sV --open -oA scans/nibbles-initial "$TARGET"
# Example follow-up when 22 and 80 were actually observed:
nmap -sC -sV -p 22,80 -oA scans/nibbles-focused "$TARGET"

16. Nibbles - Web Footprinting

A sparse home page can still reveal useful clues in its source. In this case study, a comment points toward the Nibbleblog application; Figure C shows that clue. Inspect the application, documentation, version evidence and exposed directories. Keep observed facts separate from guesses about credentials. Avoid broad password guessing: a lockout can obscure the real problem and interfere with learning.

Practice checkpoint: Explain the evidence that supports the application/version identification and the next hypothesis. 

curl -s "http://$TARGET/"
whatweb "http://$TARGET/nibbleblog/"
curl -s "http://$TARGET/nibbleblog/README"
gobuster dir -u "http://$TARGET/nibbleblog/" -w "$WORDLIST" -o scans/nibbleblog-paths.txt

17. Nibbles - Initial Foothold

Authenticated administration does not automatically mean operating-system access. The walkthrough examines whether an image-upload feature accepts executable PHP and whether the server executes the uploaded file. Figure D identifies the relevant feature. Start with a small identity proof, verify the response and effective account, then follow the lab lesson for its shell demonstration. Distinguish a UI warning from proof that an uploaded file failed.

Practice checkpoint: Record the upload behavior, resulting path and returned identity; explain the server-side trust boundary.

18. Nibbles - Privilege Escalation

The important lesson is the relationship between a sudo-authorized script and the account allowed to modify that script. Inspect the archive and file before making changes. Compare ownership and permissions with the sudo rule, and explain how running attacker-controlled script content with greater privileges changes the boundary. Record any lab changes and cleanup. Remediation includes restricting write access and removing unnecessary privileged execution.

Practice checkpoint: Write a finding with prerequisite access, the writable path, sudo evidence, impact and a concrete fix. 

unzip -l personal.zip
# Extract only inside your authorized lab workspace when appropriate.
unzip personal.zip
sudo -l
ls -l personal/stuff/monitor.sh
namei -l personal/stuff/monitor.sh
sed -n '1,80p' personal/stuff/monitor.sh

19. Nibbles - Alternate User Method - Metasploit

The framework route automates a similar application-level weakness. Compare its requirements and resulting session with your manual approach. Set the assigned target, discovered application path, obtained lab credentials and reachable callback address explicitly. Recheck options before running. Automation is most useful when you can explain the underlying request and why it should work.

Practice checkpoint: Compare manual and framework attempts: prerequisites, evidence, session type, side effects and recovery steps. 

# In msfconsole, for the assigned vulnerable Nibbles lab:
search nibbleblog
use exploit/multi/http/nibbleblog_file_upload
show options
set RHOSTS ASSIGNED_LAB_IP
set TARGETURI /nibbleblog/
set USERNAME LAB_USERNAME
set PASSWORD LAB_PASSWORD
set LHOST YOUR_VPN_IP
set LPORT 4444
show options
check
# Run only after matching the lab prerequisites and verifying options:
# run

20. Common Pitfalls

Troubleshoot from the connection outward: is the profile correct, is the tunnel up, does the route select it, is the target running, and is the relevant service listening? A failed ping alone does not establish that a host is down. A browser may also be sending traffic into a proxy whose intercept is paused. Check proxy behavior before changing system-wide networking or security settings.

Practice checkpoint: Change one variable at a time and record which observation ruled out each cause. 

ip -4 address show tun0
ip route get "$TARGET"
nc -vz "$TARGET" 80
curl --connect-timeout 5 -I "http://$TARGET/"
# Compare a direct request if you suspect a local proxy:
curl --noproxy '*' --connect-timeout 5 -I "http://$TARGET/"

23. Knowledge Check

Use the assessment as an independent test of the whole method. Enumerate services, investigate web functionality, validate a plausible weakness, obtain the required lab access and inspect privileges. Keep your own evidence trail rather than searching for a flag or copying a walkthrough. If stuck, identify the stage and smallest missing fact. A complete note should let you reproduce your work and explain a remediation.
